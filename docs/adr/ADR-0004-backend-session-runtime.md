# ADR-0004: セッションの実行モデル

- 日付: 2026-10-03
- ステータス: Proposed
- 関連: [ADR-0002](ADR-0002-backend-technology-selection.md) / [ADR-0003](ADR-0003-backend-state-and-communication.md) / [docs/backend/state-schema.md](../backend/state-schema.md)

## 背景

> どのような状況・制約・力関係のもとでこの決定が必要になったのか。

- 背景: **1つのセッションには、3人分の受信メッセージ、20Hz の配信、フェーズの締切、ワークスペースの2秒アクションの完了など、並行する入力が来る。これらをどこに置き、どの順序で処理するかで、先着判定や「締切と完了の順序」(state-schema.md §5.1)の正しさが決まる**
  - 週末までに軽くバックエンドを立て、翌週からフロントとつなぎ込む予定で、早く立ち上がる構成が求められる
  - セッションの状態は短命(1ゲームで終わる)
  - デプロイ先は未確定(バックエンドは AWS ECS の予定)

## 決定

以下の3点を採用する。

1. **状態はメモリのみで、単一プロセスで持つ**
   - 保存先は interface で切り出し、後から差し替えられるようにする
   - 終了したセッションは結果を送ってから破棄する。人間が全員切断したセッションは、一定時間(例: 60 秒)誰も戻らなければ破棄する。個人の切断には期限を設けない
1. **セッションごとに goroutine を 1 つ立て、すべての入力をひとつのチャネルから順番に処理する**
   - 受信メッセージ、配信のタイマー、締切、ワークスペースのアクション完了を同じチャネルに入れる。セッションの状態に触るのはこの goroutine だけ
   - ゲームの規則は「状態 + 入力 → 新しい状態 + 配るメッセージ」の純粋な関数にして、WebSocket と切り離してテストする
1. **送信は接続ごとの goroutine に任せ、あふれたら種類で扱いを変える**
   - `transforms` は古いものを捨てて最新だけを送る(次の配信で上書きされるため)
   - `seq` を持つ確定状態のメッセージがあふれたら、その接続を切る。再接続すれば `snapshot` で復旧する

```text
conn A ─┐
conn B ─┤
conn C ─┼─▶ inbox chan ─▶ [session goroutine]
ticker ─┤                  state + rules(純粋関数)
timers ─┘                      │
                               ▼
                      各 conn の送信キュー ─▶ 送信 goroutine
```

理由:

- メモリのみ・単一プロセス: DB なしで最も早く立ち上がり、セッションの状態は短命なので永続化の必要が薄いため
- セッションごとの goroutine とチャネル: 先着判定や処理順が構造で保証され、ロックが要らないため。セッション同士も互いに止め合わない
- 純粋な関数: フロントのダミーのサーバー役(`dummyAuthority`)のテストを移植でき、WebSocket なしで規則を検証できるため
- 送信を分ける: 1人の遅い回線が、セッションの処理や他のプレイヤーへの配信を止めないため

前提と制約:

- 状態をメモリに持つので、ECS のタスクは 1 つに固定する。再起動すると進行中のセッションは消える(Cookie は署名付きなので有効なまま。ADR-0003)
- 複数台に広げるときは、この ADR を見直す(セッションを特定のタスクに振り分ける仕組みや、外部の保存先が要る)

## 検討した選択肢

### 案B: Redis で状態を持つ

- 概要: 待機列やプレイヤー情報を Redis に置く
- 利点: 複数台構成や再起動に備えられる
- 欠点 / リスク: 構成要素が増え、開発環境(devenv)にも Redis が要る
- 却下理由: 今は単一プロセスで足り、最も早く立ち上げられるため。保存先は interface で切り出し、必要になれば差し替える

### 案C: 状態を mutex で守る

- 概要: 各接続の goroutine が、セッションの mutex を取って直接状態を書き換える
- 利点: コードが少ない
- 欠点 / リスク: タイマーとの順序や、ロックを握ったままの送信などでバグを作りやすい
- 却下理由: 先着判定と処理順の正しさを、構造で保証したいため

### 案D: 固定ティックでまとめて処理する

- 概要: 受信した入力をためておき、20Hz のティックごとにまとめて処理する(ゲームサーバーによくある形)
- 利点: 物理演算などを決まった間隔で回すのに向く
- 欠点 / リスク: インタラクトの応答が最大 50ms 遅れる
- 却下理由: 物理演算をサーバーで行わない今回は、利点が薄いため

### 案E: 送信キューがあふれたら、種類によらず切断する

- 概要: 送信キューがあふれたら、`transforms` でも切断する
- 利点: 最も単純
- 欠点 / リスク: 遅い回線では座標の溜まりだけで切れ、再接続が増える
- 却下理由: 座標は捨てても次の配信で回復するため、切断するほどではない
