# ADR-0003: バックエンドの状態モデルと通信の設計

- 日付: 2026-10-03
- ステータス: Proposed
- 関連: [ADR-0002](ADR-0002-backend-technology-selection.md) / [docs/backend/state-schema.md](../backend/state-schema.md) / [backend/api/openapi.yaml](../../backend/api/openapi.yaml)

## 背景

> どのような状況・制約・力関係のもとでこの決定が必要になったのか。

- 背景: **フロントエンドは、サーバー権威を前提にした「状態の写し + 要求の口」の作り(`frontend/src/objects`・`items`)で先行して実装されていた。一方、v0.1 の状態スキーマ案は、ファイルを `files[]` の一覧で持つなどフロントの形と食い違っており、サーバーの状態の持ち方・プレイヤーの識別・マッチングの方式を決める必要があった**
  - フロントでは、同じファイルが「ディレクトリの在庫(`objects[].data.stock`)」「手持ちアイテム(`items` の held)」「成果物の数(`outputs`)」と、いる場所によって別の構造に入る
  - サーバーには、死亡・切断時のファイル返却、フェーズごとのリセット、タスク達成の判定など、ファイルの所在を横断して扱う処理がある
  - アカウント(ログイン)は設けない
  - デプロイ先は未確定(フロントエンドは Cloudflare Workers、バックエンドは AWS ECS の予定)

## 決定

以下の5点を採用する。

1. **サーバー権威。クライアントは一切判定しない**
   - 操作は要求(`interact`)として送るだけで、サーバーが検証して結果を全員に配る
   - 同時に同じ操作が来たら、サーバーの処理上の先着で判定する。負けた側には本人にだけ `object.interactRejected` を返し、画面上は何も起きない
2. **状態は2層に分ける**
   - 内部(正となる状態): アイテム(ファイル・ライター)を所在に関係なく `items[]` の一覧で持ち、それぞれが `location`(`directory` / `held_by` / `workspace` / `object`)を持つ
   - 配信: 送る直前に、フロントの形(ディレクトリの `stock`・`outputs`、プレイヤーの `heldItem`)に組み立てる
   - ライターもアイテムとして扱い、ファイルとは同時に持てない(手は 1 つ)
3. **プレイヤーは匿名 ID を HttpOnly Cookie(`iubeo_player`)に入れて識別する**
   - 初回に `POST /api/v1/players` で発行し、HTTP にも WebSocket の接続にも自動で付く
   - 再接続しても同じプレイヤーとして復帰できる
4. **マッチングは自動。結果はまず HTTP のポーリングで受け取る**
   - `POST` / `GET` / `DELETE /api/v1/matchmaking` で、待機列に入る・状況を見る・やめる
5. **状態はメモリのみで、単一プロセスで持つ**
   - セッションごとに goroutine を立てて順番に処理する(先着判定が自然に保証される)
   - 保存先は interface で切り出し、後から差し替えられるようにする

理由:

- サーバー権威・クライアントは判定しない: 勝敗・タスク達成・ファイルの所在は3人で共有される状態であり、クライアントごとに判定すると食い違うため。フロントも既にこの前提で作られている
- 2層: 内部を一覧にすると、返却やリセットは `location` の書き換えだけで済み、ファイルが消えたり増えたりするバグが起きにくい。配信をフロントの形にすれば、フロントの `GameObject`・`Item` の型をそのまま使える
- HttpOnly Cookie: JS から読めないので安全で、フロントでトークンを扱う処理が要らない。WebSocket の接続にも自動で付く
- 自動マッチング: 知らない人とも遊べるようにするため。待ち時間の体感が悪ければ、後で WebSocket での通知に変える
- メモリのみ・単一プロセス: DB なしで最も早く立ち上がり、セッションの状態は短命(1ゲームで終わる)なので永続化の必要が薄いため

前提と制約:

- Cookie での識別は、ブラウザから見てフロントとバックエンドが同じオリジン、少なくとも同じサイトであることを前提にする。開発時は Vite の proxy で同じオリジンにする。本番の構成(Worker で中継するか、サブドメインで分けて CORS を設定するか)は、デプロイ先が決まってから決める
- 状態をメモリに持つので、ECS のタスクは 1 つに固定する。再起動すると進行中のセッションは消える

## 検討した選択肢

### 案B: フロントの形をそのまま正にする

- 概要: サーバーも `objects[].data.stock` と、プレイヤーごとの手持ちアイテムで状態を持つ
- 利点: 配信の形に変換する処理が要らない
- 欠点 / リスク: ファイルの所在が複数の場所に散らばり、移すたびに片方から消してもう片方に足す必要がある。片方を忘れるとファイルが消えたり増えたりする
- 却下理由: 返却・リセット・達成判定など、所在を横断する処理が多く、バグの温床になるため

### 案C: v0.1 の `files[]` を正にして、フロントを合わせる

- 概要: 配信も `files[]` の形で送り、フロントの `directory.data`・`items` の扱いを書き換える
- 利点: サーバーの実装が単純になる
- 欠点 / リスク: 先行して実装されているフロントの書き換えが必要になる
- 却下理由: 2層にすれば、サーバーの扱いやすさとフロントの変更の少なさを両立できるため

### 案D: プレイヤー識別をトークン + localStorage にする

- 概要: サーバーが返したトークンをクライアントが localStorage に保存し、HTTP では Authorization ヘッダー、WebSocket では最初のメッセージで送る
- 利点: フロントとバックエンドのオリジンが別でも動く
- 欠点 / リスク: トークンを送る処理をフロントで書く必要がある。JS から読めるので、XSS で盗まれうる
- 却下理由: 同じオリジンにできる前提なら、Cookie のほうが安全で実装も少ないため

### 案E: プレイヤー識別を接続ごとの使い捨て ID にする

- 概要: 永続的な ID は持たず、マッチング時に発行するセッション内だけの ID を使う
- 利点: 最も単純
- 欠点 / リスク: リロードすると再接続できない
- 却下理由: 再接続(切断から戻ったときに同じプレイヤーとして復帰する)を支えられないため

### 案F: ルームコード方式のマッチング

- 概要: 1人がセッションを作ってコードを発行し、他の2人がそのコードで参加する
- 利点: 実装が最小。知り合い同士で遊ぶ想定に合う
- 欠点 / リスク: 知らない人とは遊べない
- 却下理由: 自動で3人を組めるようにしたいため

### 案G: Redis で状態を持つ

- 概要: 待機列やプレイヤー情報を Redis に置く
- 利点: 複数台構成や再起動に備えられる
- 欠点 / リスク: 構成要素が増え、開発環境(devenv)にも Redis が要る
- 却下理由: 今は単一プロセスで足り、最も早く立ち上げられるため。保存先は interface で切り出し、必要になれば差し替える
