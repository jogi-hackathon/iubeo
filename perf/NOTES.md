# パフォーマンス計測ログ

計測の手順は `README.md`。結果は `results/baseline/`(変更前)と `results/after/`(変更後)にある。
どちらも `run-all.sh` で、通常・上限なし前進・4G+CPU4x の各 3 回、Go ベンチ 5 回、負荷試験 3 回。表の値は中央値。

## 環境

- Apple M4 / macOS(Darwin 27.0.0)、Go 1.27.1、Node 24.20、pnpm 11.25
- ブラウザ: Playwright の Chrome for Testing 153(headless、WebGPU 有効)、Playwright 1.63
- 負荷試験: 同一マシンで、サーバー(`perf/.tmp` にビルド)と負荷(30 クライアント / 10 セッション / 20Hz / 20 秒測定)を同時に動かす

## 計測の道具に直したこと(計測の誤りを先に潰した)

- 起動完了の判定: ウォームアップの被せ(`.boot-overlay`)も `.boot-screen` のクラスを持っていたため、「起動画面が消えた」を被せが消えるまで遅らせていた → `:not(.boot-overlay)` で分けた。
- 負荷試験の配信数: 助走の分まで数えて、測定時間で割っていた(7,851/秒 と出ていた) → 測定時間の中だけ数える(600/秒が正しい)。
- 負荷試験の終了: クライアントが全体の期限(助走 + 測定 + 2 分)まで止まらず、1 回ごとに 2 分余計にかかっていた → 測定の終わりに止める。
- 負荷試験の切断の数え方: 終了時の打ち切りを「切断」と数えていた(baseline の load-2 の 1 件はこれ) → 打ち切りは数えない。**baseline の切断 1 は実際の切断ではない**。
- 初回の圧縮: サーバーが初回だけ brotli q11 で時間がかかり、1 回目の起動が 3 秒になっていた → 圧縮結果をキャッシュし、捨て打ちの 1 回を入れた。

## 変更したもの

### 1. `frontend/vite.config.ts`: `three` を `three/webgpu` に寄せる

- 何が重複していたか: `three.module.js`(約 200KB)と `three.webgpu.js` の両方が入っていた。`three` の import が 40 ファイル以上あり、R3F も `three` を import しているため。
- 効果: JS 1,920KB → 1,591KB(raw、-17%)、転送量 408KB → 352KB(-14%)。4G 相当の起動が約 100ms 短くなる(1,153ms → 1,038ms)。
- 見た目: 静止画とスクリーンショットの差分で確認した。静止画は同じ(最大差 1、差のあるピクセル 0.4%。baseline 同士と同じ)。前進後の画面は、計測のたびにわずかに揺れる(前進中の時間で位置が変わる)ので、比べるのは「baseline 同士の差」(最大 10)の範囲に入るかどうか。alias 版の 2 回目と 3 回目は baseline と最大 7〜11 で、この範囲に入る。1 回目の alias 版だけ最大 56 ずれたが、2 回目以降ではこの外れは再現しなかった(タイミングのずれと見ている。原因は未確認)。
- 検証: typecheck・lint・format・テスト(48 ファイル・414 件)はすべて通る。

### 2. `backend/internal/session/session.go`: 受信を 1 回のデコードにする

- 何をしていたか: `api.ClientMessage` の union に生の JSON を入れ、`ValueByDiscriminator` が型を読み、さらに型ごとにもう一度デコードしていた(3 回パース)。
- 変えたこと: `ReceiveJSON` で type だけを先に読み、その型に 1 回だけデコードする。`Receive`(内部の API)は削除。エラー文言は従来と同じにした。
- 効果: 1 件あたり 1,357 ns → 1,101 ns(-19%)。ただし負荷試験(600 件/秒)では CPU の 0.1% にも満たず、体感や RTT には現れない。**小さな改善として入れた**。
- 検証: 既存のテスト(`invalid_message` を含む)はすべて通る。

## 調べて、適用しなかったもの

### A. シェーダーのウォームアップの待ち(提案。判断が必要)

- 現状: `WARMUP_STABLE_MS = 500`(`frontend/src/core/warmupTracker.ts`)。シーンの構成が 500ms 変わらないと、起動の被せが消えない。
- 計測: この値を一時的に 0 にすると、操作できるまでが 999ms → 約 540ms(3 回: 530 / 544 / 554)。**残りの約 450ms は待ちの床**で、シェーダーのコンパイル自体は約 540ms 中の一部。
- 提案: 例えば 150ms にすると、通常は約 650ms で操作できる(実測は未確認)。
- 不採用にした理由: この値は「読み込みが落ち着いた」を見分けるための設計値。下げると、後から非同期で入るマテリアル(ベイク AO の `holdShaderWarmup` で待たせている以外)が、操作中に初めてコンパイルされて引っかかる(スタッター)危険がある。見た目は変わらないが、読み込みの仕組みに関わるので、判断は担当者に任せる。

### B. 負荷試験の RTT(提案。仕様の判断が必要)

- RTT p50 約 44ms の大部分は、サーバーが 20Hz の tick(50ms)で transforms を配ることによる待ち。tick ごとではなく受信のたびに配信すれば、RTT は数 ms まで下がると見込まれる(未計測)。
- ただし配信の回数が増え、仕様(`state-schema.md`・ADR-0004 の 20Hz)を変える判断になる。ここでは実装しない。

### C. その他に見送ったもの

- `Step` の state の複製(clone): 1 件 300ns 程度で、受信のたびに行う設計(純粋な関数)の一部。効果に対して設計を崩すので見送り。
- PGO(`default.pgo`): サーバーは I/O が中心で CPU はほぼ使っていない。効果は小さく、プロファイルの保守が増えるので見送り。
- WebGPU のアダプタ取得の重複(`assertWebGPUAvailable` と `renderer.init`): 数 ms。失敗時のエラー文言の経路が変わるので見送り。
- 開発用パネルの遅延読み込み: 本番バンドルに入っているのは数 KB(gzip で 1% 未満)。効果が小さいので見送り。
- フレームの描画(ポストプロセス): 上限なしで 1.5ms/フレーム。ただし現在のシーンは床と壁だけ。シーンが増えたときに改めて測る。

## 残っている注意点

- 現在のシーンは「床と壁」だけ(`RoomScene` / `SandboxScene` の中身は未実装)。描画の負荷はまだ小さく、この計測では描画のチューニングの余地を判断できない。
- 起動の時間は、ほぼ JS の転送量(4G 相当)とウォームアップの待ち(A)で決まる。
- 本番の配信(Cloudflare の圧縮・キャッシュヘッダー)は、ローカルの静的配信で再現していない。デプロイ後に実測すると確かになる。

**6. バックエンド: 300 クライアント(100 セッション)の負荷**

## ラウンド 3: 前の回で見落としていたもの

### 1. 手元のビルドはデバッグが有効だった(計測の前提の確認)

- `frontend/.env`(git 管理外)に `VITE_ENABLE_DEBUG=true` があり、手元の `vite build` は本番でもデバッグ機能(GPU タイムスタンプの記録など)が有効だった。CI(`.github/workflows/deploy-cloudflare.yml`)には `.env` が無いので、本番は無効。
- 比べた結果、差は無かった(DPR 1: 1.5 ms 対 1.5 ms、DPR 2: 4.6 ms 対 4.7 ms、各 3 回)。前の回までの数値はそのまま使える。
- 以後は CI と揃えるため、`run-all.sh` は `VITE_ENABLE_DEBUG=false` でビルドする。

### 2. 再訪のたびに JS を再検証していた → `frontend/public/_headers`(採用)

- Workers Static Assets の既定は `Cache-Control: public, max-age=0, must-revalidate`。ハッシュ付きの `/assets/*.js` も、再訪のたびに往復 1 回の再検証(304)が入っていた。
- `/assets/*` に `public, max-age=31536000, immutable` を付けた(index.html は既定のまま、毎回確かめる)。
- 計測用サーバー(`lib/serve.mjs`)を Cloudflare の既定(ETag / 304 / `_headers`)に合わせ、`bench-browser.mjs --repeat`(同じコンテキストで開き直す)で測った。
- 再訪(4G 相当 + CPU 4 倍): 起動画面が消えるまで 171 / 185 / 173 ms → 149 / 164 / 151 ms(往復 1 回ぶん、約 20 ms)。実際の回線は遅延が大きいので、差はもっと大きくなる。

### 3. ウォームアップの待ちの中身を記録した(提案 A の根拠)

計測用ビルドで、ウォームアップの判定(構成の変化・hold・終了)の時刻を記録した(`lib/probe-warmup.mjs`)。

| シーン | 構成の変化 | hold の終わり | 被せが消える |
|---|---|---|---|
| room(本番の初期シーン) | 開始時の 1 回だけ | なし | +510〜530 ms |
| test(ベイク AO あり)、回線制限なし | +172〜175 ms | +159〜161 ms | +693〜717 ms |
| test、4G 相当 | +2,667〜2,671 ms | +2,647〜2,654 ms | +3,185〜3,202 ms |

- room では、開始後に構成は一度も変わらない。被せが消えるまでの約 500 ms は、まるごと「500 ms 変わらないことを確かめる待ち」。
- test でも、hold(ベイク AO の読み込み)が終わってから構成が変わるまで 15 ms 以内。
- つまり、待ちを短くしても(例: 150 ms)、今のシーンで取りこぼす変化は無い。本番の起動が約 350 ms 速くなる見込み。判断は担当者に任せる(未適用)。

### 4. ベイク AO の読み込みがウォームアップを待たせていた(採用)

test シーンを 4G 相当で開くと、ベイク AO(`/ao/test.bin` と `/ao/test.png` 1.2 MB)を読み終えるまで、被せが約 3.2 秒消えなかった。本番の room にはまだベイク結果が無いが、ベイクすれば同じことが起きる。

- **(a) 読み込みの並列化**(`src/bake/BakedAO.tsx`): レイアウト(.bin)を読み終えてから、アトラス(.png)を取りに行っていた。同時に取りに行くようにした。ベイク結果が無いときは、アトラスの失敗を握りつぶす(room でエラーが出ないことを確認)。4G 相当で +3,195 ms → +3,100 ms(約 -95 ms)。
- **(b) PNG の可逆圧縮**(`scripts/png.ts`): ベイクの PNG エンコーダが、行フィルタなしで書いていた。行ごとに最適なフィルタ(なし・Sub・Up・Average・Paeth)を選ぶようにした。`public/ao/test.png` を書き直して 1,225,783 → 910,651 bytes(-26%)。デコードした画素は、4,198,644 画素すべて同じ(最大差 0)。
- (a)+(b) で、test シーン・4G 相当の被せが消えるまで +3,195 ms → +2,465 ms(-730 ms、-23%)。ベイク AO は同じように貼られる(22 mesh / 4151 チャート、ログで確認)。

### 5. 見て、問題が無かったもの

- 他のプレイヤーの transform(20Hz)は React を通らない(サンプルを足すだけ。参加者の増減のときだけ再描画)。
- 狙いの判定(毎フレームのレイキャスト)は、変わったときだけ通知し、BVH の高速なレイキャストが有効。
- 毎フレームの React の再描画は見つからなかった。

| 受信 1 件のデコード | 1,357 ns | 1,101 ns | 1,070 ns |
| 負荷: RTT p50 / 配信間隔 p95 | 44.2 / 50.7 ms | 46.2 / 50.7 ms | 44.9 / 51.3 ms |

- 「上限なし・前進」の fps は、after2 で 516(after は 648)と出た。変更前のビルド(dist-nodebug)と変更後(dist-round3)を交互に 3 回ずつ測ると、どちらも 400〜634 fps の間で揺れ、差は無かった。マシンの状態(熱など)による揺れで、退行ではない。この指標は、同じ時間帯に交互に測ったときだけ比べる。
- JS ヒープも 12〜27 MB の間で揺れる(GC の時期による)ので、1 回の値では比べない。

## ラウンド 4: 位置のメッセージのバイナリ化(試作と実測)

### 試作の内容

- 対象は、量の大半を占める位置のメッセージ(クライアント → サーバーの transform、サーバー → クライアントの transforms)だけ。頻度の低いメッセージは JSON のまま。
- 形式は固定レイアウトの自前バイナリ(Protobuf は使わない。依存とコード生成を増やさないため)。`backend/internal/session/binary.go` に定義した。
  - transform(25 B): 種別 | seq u32 | 位置 f32×3 | yaw f32 | pitch f32
  - transforms(10 + 25n B): 種別 | serverTime f64 | 人数 | n × (席 u8 | seq u32 | f32×5)。playerId(26 文字)の代わりに席を送る(席と playerId の対応は snapshot で配っている)
- WebSocket の URL に `enc=bin` を付けた接続だけがバイナリになる。今のフロント(JSON)はそのまま動く。**フロント側の対応は未実装**(使うには、受信・送信の両方を足す必要がある)。
- 負荷試験に `-binary` と送受信量の計測を足した。`perf/ws-ab.sh` で、JSON とバイナリを交互に測り、測定時間の間のサーバーの CPU 時間も記録する。
- テスト: コーデックの往復・席の置き換えのテストを追加。既存のテストもすべて通る。golangci-lint 0 件。

### 結果

**コーデック単体(Go ベンチ、3 回)**

| 処理 | JSON | バイナリ |
|---|---:|---:|
| 配信 1 回のエンコード(3 人分) | 855 ns・384 B・2 allocs | 31 ns・96 B・1 alloc |
| 受信 1 件のデコード | 1,066 ns・216 B・6 allocs | 61 ns・104 B・2 allocs |

**負荷試験(交互に測定)**

| 指標 | JSON | バイナリ | 変化 |
|---|---:|---:|---:|
| 受信(1 クライアント、ペイロード) | 9,145 B/秒 | 1,700 B/秒 | -81% |
| 送信(1 クライアント、ペイロード) | 1,789 B/秒 | 500 B/秒 | -72% |
| 受信(TCP/IP・WebSocket のヘッダ込みの見積もり) | 約 10.2 KB/秒 | 約 2.8 KB/秒 | 約 -72% |
| サーバー CPU、30 クライアント(3 組) | 7.7〜7.8% | 6.9〜7.2% | 約 -9% |
| サーバー CPU、300 クライアント(4 組) | 42.7〜50.4%(中央値 45.2%) | 42.0〜47.2%(中央値 42.8%) | 約 -5%(揺れの範囲に近い) |
| RTT p50、30 クライアント | 38.7〜42.5 ms | 42.4〜45.5 ms | 一貫した差なし(tick 待ちが支配) |
| 配信間隔 p95 | 50.5 ms 前後 | 50.8 ms 前後 | 差なし |

### 判断

- 効くのは**転送量**(下り約 -80%、ヘッダ込みで約 -70%)。モバイル回線のデータ量と、サーバー側の転送料金に効く。
- サーバーの CPU は数 % しか減らない。CPU の大半は 1 通ごとの syscall で、メッセージの数は変わらないため。
- RTT は変わらない。20Hz の tick 待ちが支配しているため。
- 採用するなら、仕様(openapi.yaml、state-schema.md、ADR-0004)とフロントの受信・送信の対応が要る。判断は担当者に任せる。試作のサーバー側は、enc=bin を付けない限り今の動作と同じ。

### もっと詰められるか(試算。`lib/estimate-packing.mjs`、`lib/estimate-deflate.mjs`)

前提: フロントは transforms の `serverTime` を使っていない(grep で確認)。`seq` は「増えたか」の比較だけに使う。座標は床の範囲(±100 m)に収まる。

**v2 案**(v1 からさらに詰める):

- serverTime を送らない。
- 席は、1 人ごとの 1 B ではなく、ビットマスク 1 B で表す。
- seq は u16(比較は桁あふれを考える)。
- 位置は i16(1/256 m 刻み、±128 m)。
- yaw は u16、pitch は i16。

| 形式 | 下り 1 通(3 人) | 上り 1 通 | 下り 回線(ヘッダ込み・20Hz) | 上り 回線 |
|---|---:|---:|---:|---:|
| JSON(今) | 456 B | 89 B | 10.64 KB/秒 | 3.38 KB/秒 |
| JSON + permessage-deflate(試算) | 約 105〜120 B | - | 約 3.6〜3.9 KB/秒 | - |
| v1(試作済み) | 85 B | 25 B | 3.22 KB/秒 | 2.10 KB/秒 |
| v2(案) | 38 B | 13 B | 2.28 KB/秒 | 1.86 KB/秒 |

- v2 の量子化の誤差: 10 万回の往復で、位置は最大 1.95 mm、yaw は 0.0027°、pitch は 0.0014°。画面では見分けられない大きさだが、値はわずかに変わる。
- 回線のヘッダは 1 通あたり約 76 B(TCP/IPv4 52 B + TLS 22 B + WebSocket 2〜6 B)。v1 の時点で、ペイロードよりヘッダのほうが大きい。v2 にしても、回線上は下り -29%、上り -11% にとどまる。
- これ以上削るなら、差分の符号化(前回との差を int8 で送る)がある。ただし、配信は「最新だけ送り、古いのは捨てる」作りなので、差分の基準がずれる。基準フレームや確認応答の仕組みが要り、複雑さに見合わない。
- 回線上の量を本当に減らすなら、通数(20Hz)を減らすのが一番効く。ただし、他プレイヤーの動きの滑らかさに関わる、仕様の判断になる。
- 仕様を変えずに済む案: WebSocket の圧縮(permessage-deflate)。JSON のままで約 8 割減り、v1 とほぼ同じになる。ただし、接続ごとの圧縮の CPU とメモリ(文脈の窓)がかかる。Cloudflare の Worker を通した経路で有効になるかは、未確認。

## ラウンド 5: WebSocket の圧縮(permessage-deflate)を実際に試した

### やったこと

- サーバー: `IUBEO_WS_COMPRESSION`(`off` / `context-takeover` / `no-context-takeover`。既定 `off` で、今の動作のまま)を追加した(`internal/config`、`server.SetWSCompression`)。設定のテストを追加した。
  - `no-context-takeover` は、512 B 以上のメッセージだけを圧縮する(coder/websocket の既定)。transforms は 1 通 450〜600 B で、ほとんど効かない。比べたのは `context-takeover`(128 B 以上、メッセージをまたいで辞書を使う)。
- 負荷試験:
  - `-compress`(圧縮を要求する)を追加した。
  - TCP の上で実際にやり取りしたバイト数(WebSocket のヘッダ込み、圧縮後)を数えるようにした。
  - **動きを実際に近づけた**。今までは位置が固定で、向きだけが変わっていたため、圧縮が効きすぎて出た(受信 -90%)。クライアントごとに位相をずらした円を歩き、進行方向を向き、上下も見回すようにした。このため JSON の 1 通が約 590 B になった(小数の桁が全部出るため)。
- `perf/ws-ab.sh` を 3 方式(json / compress / binary)の交互測定に広げ、サーバーのメモリ(RSS)も記録するようにした。

### 結果(交互に測定。30 クライアント 3 組、300 クライアント 2 組)

| 指標 | JSON | JSON + 圧縮 | バイナリ(試作) |
|---|---:|---:|---:|
| 回線 受信(1 クライアント、WebSocket ヘッダ込み) | 12,005 B/秒 | 2,778 B/秒(-77%) | 1,740 B/秒(-86%) |
| 回線 送信 | 2,877 B/秒 | 1,358 B/秒(-53%) | 620 B/秒(-78%) |
| サーバー CPU・30 人 | 6.8〜8.2% | 9.8〜10.9%(約 +35%) | 4.5〜7.5% |
| サーバー CPU・300 人 | 31.1〜34.2% | 46.3〜48.9%(約 +45%) | 34.4〜36.0% |
| サーバー メモリ・30 人 | 20〜21 MB | 57〜60 MB | 19〜21 MB |
| サーバー メモリ・300 人 | 39〜40 MB | 407〜432 MB(約 1.3 MB / 接続) | 39〜40 MB |
| RTT | - | - | 方式による一貫した差なし(tick 待ちが支配) |

- 同じ JSON のまま、プロトコルもフロントも変えずに、受信が約 8 割減る。
- その代わり、サーバーの CPU が 4 割前後増え、メモリは 1 接続あたり約 1.3 MB 増える(1.2 MB の圧縮器を接続ごとに持つため)。本番は t4g.small(2 vCPU、2 GB)で、コンテナのメモリ上限が 1,024 MiB(`infra/aws/terraform/variables.tf`)なので、約 700 接続で上限に届く計算になる。
- Safari は permessage-deflate に対応していない(圧縮なしでつながるだけで、壊れはしない)。
- Cloudflare Workers の WebSocket の圧縮は、compatibility date 2023-08-15 以降で有効(このプロジェクトは 2026-10-01)。ただし、フロント Worker → バックエンド Worker → コンテナの経路で、圧縮が端から端まで交渉されるかは未確認。
- 比べると、バイナリのほうが減り方が大きい。しかも CPU とメモリは増えない。ただし、仕様とフロントの対応が要る。

### 判断

- すぐに試すなら、圧縮は設定 1 つで有効にできる(既定はオフのまま入れてある)。ただし CPU とメモリの増加が大きく、帯域の削減と引き換えになる。
- 長く使うなら、バイナリ(v1)のほうが割に合う。どちらにするか、あるいはどちらもしないかは、担当者の判断。
